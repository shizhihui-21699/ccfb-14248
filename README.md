# provchain — 构建来源证明 (Build Provenance Attestation)

一套 Go 实现的构建来源证明体系, 模型借鉴 [in-toto](https://in-toto.io) / [SLSA](https://slsa.dev):
每个发布产物附带一条**可验证的证明链**, 记录它由哪份源码、在哪个构建环境、
用哪些依赖、经过哪些步骤产生; 客户安装前可以独立核验。

## 运行演示

```sh
go run ./cmd/provdemo demo      # 完整演示: 诚实流水线 + 客户核验 + 可复现性 + 4 个篡改场景
go run ./cmd/provdemo run       # 只跑诚实流水线 + 客户核验
go run ./cmd/provdemo attacks   # 只跑篡改场景
```

演示会在 `demo-run/` 下搭建一个模拟世界: 源码仓库、依赖仓库、签名密钥、
内容寻址存储(CAS)、构建机目录、发布目录。

## 架构

```
 开发者                构建机 (不可信)              签名服务 (独立, 持密钥)
─────────          ─────────────────────      ──────────────────────────────
 源码 ──┐            1. fetch-source  ──报告──▶ 记录源码快照
 依赖 ──┼─ lockfile  2. resolve-deps ──报告──▶ 逐条比对 lockfile
 (锁定摘要)          3. build         ──报告──▶ 材料必须已签发过
                     (无签名密钥)                + 从 CAS 取料独立重建,
                       │                         摘要一致才签名
                       ▼                        4. package: 只打包已签发产物
                    CAS (内容寻址存储) ◀──────── 按摘要取料, 完整性校验
                       │
 客户 ◀── 产物 + 证明链(attestation.bundle.json) ──┘
   │
   └─ 独立核验: 验签 → 链完整性 → 产物摘要 → lockfile → (可选)自己重建比对
```

### 关键角色

| 组件 | 位置 | 职责 |
|---|---|---|
| `pkg/attest` | 库 | in-toto 风格 Statement/Link/Envelope、ed25519 签名、链验证 |
| `internal/signer` | 独立服务 | 持密钥, 按策略核验构建报告后才签名; 维护已签发日志 |
| `internal/pipeline` | 构建机 | 四级流水线, 每步提交构建报告换取签名 |
| `internal/verify` | 客户侧 | 只信签名公钥 + lockfile 的独立核验器 |
| `internal/cas` | 存储 | 内容寻址存储, 按 sha256 存取源码快照和依赖 |
| `internal/attacks` | 攻击者 | 四种篡改场景 |

## 难点与对策

| 难点 | 对策 |
|---|---|
| **构建机可能被攻破并伪造说明** | 签名密钥不在构建机上。构建机只提交"构建报告", 独立签名服务核验后才签名。伪造的说明没有受信签名(场景 2b); 掉包产物后, 签名服务**独立重建比对**发现摘要不一致直接拒签(场景 2a)。 |
| **依赖可能在构建中被临时替换** | 依赖摘要在 lockfile 中锁定, 拉取时校验(场景 3a); 即使在校验后、编译前掉包, 签名服务从 CAS 取的是已存证的依赖, 重建结果与构建机上报的产物不一致, 拒签(场景 3b)。 |
| **同源码不同时间构建有细微差异** | 可复现构建: `-trimpath -buildvcs=false -ldflags=-buildid=` + 关闭 CGO, 打包用确定性 tar.gz(排序、时间戳置零)。演示中隔时间构建两次, 产物逐字节一致。摘要比对因此可行。 |
| **签名密钥不能放在构建机上** | 私钥只在签名服务(演示中 `keys/`, 生产应放 HSM/KMS)。构建机目录里没有任何密钥材料。 |
| **多级流水线的说明要能串起来** | 每步的 Statement 记录输入材料(materials)的摘要, 且必须引用上一步产物的摘要; 签名服务只给"材料全部已签发过"的步骤签名。客户端核验步骤序列、衔接关系、签名三者齐备(场景 4: 拼接链、旧链重放都被识破)。 |

## 篡改场景演示结果

| 场景 | 攻击手法 | 识破机制 |
|---|---|---|
| 1. 传输中掉包产物 | 替换发布 tar 包, 证明链不动 | 产物摘要 ≠ 链尾签名摘要 |
| 2a. 构建机掉包产物求签名 | 编译后换成后门二进制再送签 | 签名服务独立重建, 摘要不一致 → 拒签 |
| 2b. 构建机伪造证明 | 自生成密钥伪造 build 环节 | 客户只信签名服务公钥 → 验签失败 |
| 3a. 拉取前污染依赖仓库 | 替换 registry 里的依赖 | lockfile 校验当场拦下 |
| 3b. 编译前掉包依赖 | lockfile 校验后替换构建目录里的依赖 | 签名服务重建比对 → 拒签 |
| 4. 拼接/重放证明链 | 把另一次真实发布的环节塞进链里 | 链式衔接断裂 / 产物摘要不匹配 |

## 生产化还需要什么(本演示的简化)

- **签名密钥**: 演示用文件密钥, 生产应放 HSM/KMS 或走 [Sigstore/Fulcio](https://docs.sigstore.dev) 短期证书。
- **透明日志**: 把签发的 Statement 追加到 Rekor 类透明日志, 防签名服务自身被攻破后悄悄签恶意见证, 也支持客户审计"这个产物是否在公开日志里"。
- **多构建者共识**: 演示是"签名服务独立重建", 生产可用 N 个互相独立的构建器 + 阈值签名(如 2/3 一致才放行)。
- **真实依赖生态**: 演示用本地 registry 模拟, 生产应对接 go module proxy 的 sumdb、容器镜像 digest 等。
- **隔离构建环境**: 每步在一次性容器/微 VM 里执行, 限制网络, 材料全部经 CAS 进出。
